# 2026-09-08 — Cluster boundary fix (Task 1)

## Task 1: Per-column cluster grouping in TreeView.tsx

**Asked:** Execute Task 1 of the `cluster-boundary-fix` SDD plan — fix `.family-cluster` boxes in the ancestor-row renderer so they group by each column's own resolved surname (via `clusterLabel`) instead of boxing an entire row-unit (couple + both sides' revealed siblings) under one shared label, which was wrong whenever a revealed sibling didn't share the couple's surname (e.g. a married-in spouse's own birth-family sibling).

**Done:**
- `client/src/components/tree/TreeView.tsx`: added `ReactNode` import; added `ColumnSegment` type and `groupSegmentsIntoClusters` helper (partitions an ordered list of `{id, label, node}` segments into adjacent same-label boxed clusters, leaving null-label segments unboxed); replaced the plural `renderSiblingColumns(ids, reserveTopSlot)` with a singular `renderSiblingColumn(sibId, sibling, sibSpouse, reserveTopSlot)`; rewrote the `row.units.map` render callback to build one `ColumnSegment` per couple-column and per revealed sibling (each independently labeled via `clusterLabel`), then group them via `groupSegmentsIntoClusters` when `row.units.length > 1 || distinctLabels.size >= 2`, otherwise render segments unboxed.
- `client/src/components/tree/TreeView.test.tsx`: updated the pre-existing test (fixture has no last names) to assert no `.family-cluster` box is drawn, per the brief's documented deliberate behavior change; added two new regression tests per the brief (a revealed sibling from a different lineage gets its own cluster, separate from their married-in relative's; a revealed sibling sharing their partner's surname gets no unnecessary box).
- **Deviation from the brief:** two of the brief's new test assertions used `screen.getByText('Santosh')` / `screen.getByText('Shobha4')` as exact string matches. `PersonPatch.tsx` (line 23) renders a person's name as `[first_name, last_name].join(' ')` in a single text node, so once those fixture people were given last names (`Santosh Khandgaonkar`, `Shobha4 Gade`), the exact-match queries failed with RTL's "text is broken up by multiple elements" error. Root-caused via the actual RTL error, confirmed the `.family-cluster-label` queries (`'Gade'`, `'Khandgaonkar'`) were unaffected (separate element, not part of the concatenated name). Fixed by adding `{ exact: false }` to the four affected `getByText` calls (two per new test) — same lookup intent, tolerant of the last-name suffix. No other test content changed.

**Outcome:** `npm test` — 18 test files, 161 tests, all passing. `npx tsc --noEmit` — clean, no output. Committed as `9f08448` — "Group family-cluster boxes by actual resolved surname, not by row-unit" (`client/src/components/tree/TreeView.tsx`, `client/src/components/tree/TreeView.test.tsx`).

## Task 2: Fix findings from whole-branch final review

**Asked:** Fix four findings (2 Important, 1 Important, 1 Minor) raised by a final whole-branch review of the cluster-boundary-fix work: (1) the `row.units.length > 1` two-unrelated-lineages guarantee was silently broken for a couple with a null resolved surname — it rendered bare instead of boxed; (2) a new intra-row vertical misalignment when boxed and unboxed columns share a row (bare columns sit higher since `.family-cluster` adds padding/border); (3) the same-label merge path (2+ adjacent segments collapsing into one box) was never exercised by any test; (4) two stale comment references to the removed `renderSiblingColumns` (plural) function name.

**Done:**
- `client/src/components/tree/TreeView.tsx`: `groupSegmentsIntoClusters` now takes a `forceLeadBox: boolean` param. When true (passed as `row.units.length > 1` from the call site) and the first segment (always the couple) has a null label, it still renders inside a real `.family-cluster` box, just without the caption div — restoring the multi-lineage separation guarantee at couple-segment granularity. Any other null-label segment reached by this function (which only runs when `shouldGroup` is already true) now renders wrapped in a new `.family-cluster-spacer` div instead of bare, so it baseline-aligns with genuinely boxed neighbors.
- `client/src/styles/global.css`: added `.family-cluster-spacer` — same padding/border width/radius as `.family-cluster`, transparent border color.
- `client/src/components/tree/TreeView.test.tsx`: fixed the two stale `renderSiblingColumns` comment references to `renderSiblingColumn`; added three tests — a multi-lineage-row null-label-couple boxing test, a null-label-sibling spacer-alignment test, and a same-label adjacent-merge test (the previously unexercised headline behavior). Also hit and fixed a test-authoring bug along the way: `SiblingFlap`'s button text is always the numeric count regardless of open/closed state, so a naive "click every `getByText('1')`" loop across two flaps in one unit never terminates safely — switched to polling `document.querySelector('.sibling-bubble:not(.open)')` in the two new tests that open two flaps.

**Outcome:** `npm test` — 18 test files, 164 tests, all passing (161 → 164, +3 new tests). `npx tsc --noEmit` — clean. Verified zero remaining `renderSiblingColumns` references via `grep -rn "renderSiblingColumns" client/src/`. Full report at `.superpowers/sdd/2026-09-08-cluster-boundary-fix/final-fix-report.md`. Nothing left open — the three explicitly-triaged follow-ups (null-label sibling next to labeled couple, the A/B/A three-box case, `addSiblingSegments` refactor) were intentionally left untouched per the review's own triage.
